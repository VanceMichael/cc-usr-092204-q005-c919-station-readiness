# C919新航点保障放行领域模型

## 背景

首航公告发布后，机场同时承诺专属值机、航显、廊桥、行李和机务保障，但任何一项临时缺位都可能让C919航班在旅客到场后才发现无法按计划运行。运行控制部门以**逐航点放行**为核心服务，把机场、机型、航线、保障单位、人员资质、备件工具、廊桥兼容和演练结果组装成可评估、可冻结、可回放的能力版本。

## 核心实体

### 航点能力版本 CapabilityVersion

- 维度：航点 × 机型 × 航线。
- 内容：保障项集合，每项登记状态、提供方与替代措施。
- 状态机：`draft → effective → frozen → retired`。
- 新航季或换机计划必须**冻结**当日采用的版本；冻结后任何变化产生新版本号，当日航班始终引用冻结版本，不被后续修订影响。

保障项编码与含义：

| 编码 | 含义 |
| --- | --- |
| `checkin` | 专属值机 |
| `fids` | 航显 |
| `jetbridge` | 廊桥兼容 |
| `baggage` | 行李保障 |
| `maintenance` | 机务保障 |
| `parts` | 备件工具 |
| `personnel` | 人员资质 |
| `drill` | 演练结果 |

保障项状态：`ready`（可用）/ `degraded`（降级）/ `absent`（缺位）。降级或缺位必须登记替代措施（措施内容 + 提供方），否则构成放行缺口。

### 放行结论 ReleaseDecision

- 针对（航班， 航班日期）,引用一个已冻结的能力版本。
- 结论取值：`go`（放行）/ `conditional`（条件放行）/ `no_go`（不放行）。
  - 全部保障项可用 → `go`；
  - 存在缺口但每个缺口均有替代措施 → `conditional`；
  - 存在无替代措施的缺口 → `no_go`。
- 放行前必须向签派员呈现三要素：**尚缺条件、替代措施、最后责任人**,缺一不可出具结论。

### 确认 Confirmation

- 机场与航司双方确认汇入**同一个**生效结论；同一放行对象只存在一个生效结论。
- 并发产生的重复结论按（决定时间， 结论编号）确定性仲裁，优胜者生效，其余置为 `superseded`,仲裁结果与提交顺序无关（幂等）。
- 双方确认引用的能力版本不一致 → 判定冲突，必须重新评估，不得各自生效。

### 运行事件 OperationalEvent

- 三条流：`aircraft`（飞机流）/ `passenger`（旅客流）/ `baggage`（行李流）。
- `occurred_at`（真实发生时间）与 `recorded_at`（系统记录时间）分离。
- 异地团队断网补录：`recorded_at` 晚于 `occurred_at`,回放按 `occurred_at` 归位并标注 `backfilled`;`recorded_at` 早于 `occurred_at` 视为数据错误，拒绝载入。

## 业务规则

| 编号 | 规则 |
| --- | --- |
| R1 | 当日放行必须引用当日冻结的能力版本 |
| R2 | 人员调班、设备故障、强对流运行限制、临时机位变化触发重算，产生新评估，历史评估保留 |
| R3 | 已售票航班保障降级必须显式审批并记录，禁止静默降级 |
| R4 | 机场与航司并发确认只产生一个生效结论 |
| R5 | 敏感维修资料按岗位隔离（字段级） |
| R6 | 补录事件保留真实发生时间，回放按发生时间排序 |
| R7 | 放行前必须呈现缺口、替代措施与最后责任人 |

## 岗位与可见性

| 岗位 | 放行结论 | 保障项状态 | 维修敏感明细 |
| --- | --- | --- | --- |
| 签派员 `dispatcher` | ✓ | ✓ | 仅结论性摘要 |
| 机场运行 `airport_ops` | ✓ | ✓ | ✗ |
| 机务 `maintenance` | ✓ | ✓ | ✓ |
| 审计 `auditor` | ✓（只读全部） | ✓ | ✓ |

携带 `sensitivity` 标记的节点对无权限岗位整体替换为 `[按岗位隔离]`,不泄露字段名与结构。

## 回放

一次延误或保障差错可按事件流回放飞机流、旅客流、行李流的完整决策链：事件按 `occurred_at` 排序（同刻按 `recorded_at`、事件编号次序）,补录事件标注 `backfilled`,敏感明细按回放者岗位过滤后呈现。
